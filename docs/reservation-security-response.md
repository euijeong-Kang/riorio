# 기존 예약 보안 대응 준비

상태: 검토안. 운영 설정이나 데이터는 변경하지 않았다.

| 항목 | 담당자 | 우선순위 | 영향 범위 | 조치안 | 검증 방법 |
| --- | --- | --- | --- | --- | --- |
| 공개 예약·대기 조회 및 디버그 응답 | 미지정 | 긴급 | 고객 개인정보·고객 조회 | 접근 제한, 디버그 응답 및 개인정보 로그 제거 | 비운영 환경에서 비인가 요청 거부와 정상 고객 조회 확인 |
| 인증 없는 관리자 함수 | 미지정 | 긴급 | 예약·대기 추가·변경·삭제 및 관리자 업무 | 서비스 역할 함수 접근 제한과 관리자 인가 설계 | 비관리자 거부, 관리자 작업·감사 기록 검증 |
| 공개 테이블 권한·정책 | 미지정 | 긴급 | 직접 Data API와 기존 연동 | 권한·정책 및 API 노출을 함께 검토 | 익명·인증 역할별 최소 권한 검사 |
| 노출 범위 및 사고 대응 | 미지정 | 긴급 | 고객·운영·규제 대응 | 로그 및 증거 보존, 담당자와 노출·회전·신고 검토 | 접근 기록과 조치 결과를 담당자가 검토 |

담당자, 적용 일정과 운영 변경 승인은 아직 미정이다. 미해결 상태를 화면 시안 완료와 혼동하지 않는다.

## 확인된 위험

운영 메타데이터와 배포 함수 소스의 읽기 전용 확인에서 예약·대기·관리자 테이블의 공개 권한과 과도한 RLS 정책, 인증되지 않은 예약·대기 조회 및 서비스 역할을 사용하는 일부 수정·삭제 함수가 확인됐다. `get-waitlist`는 다른 대기 기록의 일부를 디버그 응답에 포함하도록 작성돼 있다. 실제 외부 접근과 악용 여부는 확인하지 않았다. 세부 내역은 `christmas-reservation-development-guide.md`를 참고한다.

## 운영 승인 후 대응 순서

1. 담당자를 지정해 현재 함수·정책·권한·소비자와 복구 지점을 기록하고, 고객 조회·관리 중단 가능성을 공유한다. 필요한 로그와 증거를 보존하고 개인정보 노출을 최소화한다.
2. 직접 Data API 접근과 취약 Edge Function을 모두 통제하는 방안을 검토한다. 서비스 역할 함수는 RLS 제한만으로 보호되지 않는다. 공개 접수 중단과 기존 고객·관리 업무의 안전한 대체 경로를 함께 마련한다.
3. 관리자 인증·인가와 고객 소유 확인을 별도로 재설계하고 최소한의 정보만 반환한다. 대기 디버그 응답과 개인정보 로그를 제거한다. 서비스 역할 키는 서버에만 둔다.
4. 비운영 환경에서 접근 제어 및 기존 기능을 검증한 뒤 별도 승인으로 운영에 적용한다. 로그·접근 이력을 보존해 노출 범위, 자격증명·세션 회전, 관련 신고 필요성을 담당자와 검토한다.
5. 복원 전 비인가 조회·수정·삭제 차단과 정상 관리자·고객 흐름을 검증한다. 기존 예약 데이터를 임의 삭제하지 않는다.

## 미실행

실제 외부 요청, 침투 시험, 운영 예약 데이터 조회, 접근 차단 및 비밀정보 회전은 수행하지 않았다. 보안 조치의 구체적인 적용 방법과 일정은 운영 담당자의 승인과 시스템 영향 확인이 필요하다.
