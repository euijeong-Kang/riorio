# 근무표 게시 운영 절차

## 데이터 분리

1. 원본: 외부 비공개 보관소의 엑셀. 웹 프로젝트의 `public` 아래에 두지 않는다.
2. 검토본: `schedule-data/review/*.review.json`. 해석 후보와 확인 필요 항목을 담으며 직원 화면에서 읽지 않는다.
3. 게시본: `public/data/schedule/<주차>.<버전>.json`. 검토 완료 일정만 담는다.
4. 현재 버전: `public/data/schedule/current.json`. 직원 화면이 읽을 게시본 파일명만 가리킨다.

운영 환경에서는 `schedule_versions` 테이블의 `published` 행이 현재 게시본이다. 정적 JSON과 로컬 저장소는 Supabase 환경 변수가 없는 개발 환경의 폴백이다.

## Supabase 설정

1. 기존 리오리오 Supabase 프로젝트에 `supabase/migrations/202609130001_schedule_system.sql`을 적용한다.
2. Supabase Auth에서 관리자 이메일 계정을 직접 생성한다. 공개 회원가입 UI는 만들지 않는다.
3. 생성된 `auth.users.id`를 SQL 파일 끝의 예시처럼 `schedule_admins`에 등록한다.
4. 배포 환경에 `VITE_PUBLIC_SUPABASE_URL`, `VITE_PUBLIC_SUPABASE_ANON_KEY`를 설정한다.
5. `/schedule/admin`에서 이메일과 비밀번호로 로그인한다.

브라우저에는 publishable/anon key만 둔다. secret 또는 service-role key를 프론트엔드 환경변수에 넣지 않는다.

## 게시 순서

1. 새 엑셀의 날짜, 시간축, 병합 범위, 직원 이름과 메모를 검토한다. 여러 주차 파일은 한 번에 선택할 수 있다.
2. 직전 게시본과 직원별 추가·삭제·시간 변경을 비교한다.
3. 모든 차이를 매니저가 승인한 뒤 새 버전 파일을 만든다. 기존 파일은 수정하거나 삭제하지 않는다.
4. `npm run schedule:validate`로 등록 직원, 시간 형식, 겹침, 원본 위치, 검토 상태와 7일 게시 완전성을 검사한다.
5. 검증 성공 후에만 `current.json`을 새 버전 파일로 변경한다.
6. 오류가 발생하면 `current.json`을 변경하지 않아 직전 정상 게시본을 유지한다.

## 롤백

`current.json`의 `file`을 직전 정상 버전 파일명으로 되돌리고 다시 빌드한다. 버전 파일은 덮어쓰지 않으므로 비교 기준과 복구 이력이 유지된다.

## 현재 제한

- 포함된 게시본은 화면 검증용 샘플이며 실제 운영 게시본이 아니다.
- 직원 화면은 운영 결정에 따라 전체 주간 일정을 기본 공개하고 개인 일정은 편의용 필터로 제공한다.
- 여러 게시 주차는 직원 화면의 이전·다음 버튼과 주차 선택 메뉴로 이동한다.
- 직원 명단은 주차별 원본에서 생성하므로 새 이름은 자동 추가되고 빠진 이름은 해당 주차에서 표시되지 않는다.
- `/schedule/admin`에서 실제 `.xlsx`를 선택하고 퇴근 시각 규칙을 지정한 뒤 검토·게시할 수 있다.
- 현재 관리자 게시는 같은 브라우저의 로컬 저장소에만 반영된다. 다른 직원 기기에 전달하려면 인증된 서버 저장소 연결이 필요하다.
- 자동 알림과 서버 기반 관리자 게시는 아직 구현하지 않았다.
