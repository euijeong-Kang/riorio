## 2026-11-22 운영 메타데이터 읽기 전용 점검 — 긴급 검토 필요

연결된 운영 프로젝트에서 예약 행이나 개인정보 값은 읽지 않고 스키마·권한 메타데이터만 확인했다. `public.admins`, `public.reservations`, `public.waitlist` 모두 RLS가 활성화되어 있지만, `anon`에 세 테이블의 SELECT·INSERT·UPDATE·DELETE 테이블 권한이 있다. 실제 행 접근에는 RLS와 API 노출 설정이 함께 적용된다.

- `admins`: PUBLIC SELECT 정책 조건이 `true`이며 관리자 비밀번호 해시 컬럼이 존재한다.
- `reservations`: PUBLIC SELECT의 조건과 INSERT의 검사 조건이 각각 `true`다. 이름·전화번호·이메일 등 개인정보 컬럼이 존재한다.
- `waitlist`: PUBLIC ALL 정책의 조건과 검사 조건이 모두 `true`다. 개인정보 컬럼이 존재한다.

이 조합은 Data API 노출 및 외부 접근 가능 여부에 따라 관리자 인증 정보와 예약·대기 개인정보의 조회, 예약 추가, 대기 정보 변경 위험을 초래할 수 있다. 실제 외부 악용이나 데이터 유출 여부는 확인하지 않았고, 민감 데이터 조회·침투 시도는 하지 않았다. 운영 관리자에게 즉시 알리고 Data API 노출, 실제 접근 경로, 현재 인증과 모든 소비자를 점검해야 한다. 백업과 접근 통제 조치, 비밀번호·세션 회전 및 로그 검토는 담당자가 영향 범위와 대응 절차를 확인해 수행한다. 정책을 임의 수정하면 기존 기능이 중단될 수 있으므로 승인 없이 운영 설정은 변경하지 않았다.

연결된 프로젝트는 운영 프로젝트 한 개만 확인되었으며 별도 비운영 프로젝트는 확인되지 않았다. 가상 예약과 스키마 테스트는 별도 환경 확보 후에만 진행한다.

### 후속 배포 메타데이터 확인

운영 프로젝트에 개발 브랜치는 없다. 배포된 `get-reservations`, `create-reservation`, `get-my-reservation`, `cancel-my-reservation`, `add-reservation`, `update-reservation`, `delete-reservation`, `get-all-waitlist`, `update-waitlist`, `delete-waitlist` 등은 활성 상태이고 게이트웨이 JWT 검증 설정이 꺼져 있다. 이 설정만으로 함수 내부 인가가 없다고 단정할 수는 없으며, 배포된 함수 본문과 실제 접근 가능 여부는 아직 대조하지 않았다. 특히 예약·관리 함수의 서버 측 인가와 공개 접근 범위는 운영 담당자가 우선 확인해야 한다. 함수 호출이나 운영 데이터 변경은 하지 않았다.

`get-reservations`의 실제 배포 소스도 읽기 전용으로 확인했다. 해당 함수는 자체 인증·인가 검사 없이 익명 키로 예약 테이블의 모든 컬럼을 조회하여 반환하도록 작성되어 있으며 JWT 게이트웨이 검증도 꺼져 있다. 위에서 확인한 테이블 권한·RLS 정책과 결합할 때 예약 개인정보 노출 위험이 매우 높다. 실제 엔드포인트 호출, 예약 행 조회, 외부 노출 확인은 하지 않았고 다른 함수의 배포 본문은 아직 확인하지 않았다. 기존 사용자를 고려한 차단·권한 수정과 사고 대응을 운영 담당자와 즉시 진행해야 한다.

### 운영 함수 본문 추가 확인

2026-11-22 배포된 함수 소스를 읽기 전용으로 확인한 결과, 다음 함수들은 게이트웨이 JWT 검증이 꺼져 있고 본문에 관리자 인증·인가 검사가 없다. 실제 함수를 호출하거나 예약 행을 읽고 변경하지 않았다.

- `get-all-waitlist`: 서비스 역할 키로 대기 기록 전체 컬럼을 반환한다.
- `update-reservation`, `delete-reservation`: 서비스 역할 키로 요청된 예약의 상태·결제 상태를 변경하거나 삭제한다.
- `add-reservation`: 익명 키로 예약을 추가하며 테이블 정원 제한을 무시한다.
- `get-my-reservation`: 전화번호만으로 예약 전체 컬럼을 반환한다.
- `cancel-my-reservation`: 예약 ID와 전화번호로 대조한 뒤 서비스 역할 키로 취소한다. 실제 본인 소유 증명과는 다르다.

따라서 개인정보 조회뿐 아니라 예약의 무단 추가·변경·삭제 가능성도 긴급 조사 대상이다. 외부 네트워크 도달 여부 및 과거 악용 여부는 확인하지 않았다. 나머지 관리·대기 함수도 전수 조사해야 한다. 즉시 운영 담당자에게 알리고 서비스 중단·고객 영향과 증거 보존을 고려한 차단 방안을 승인받아야 한다. 보안 조치가 기존 기능에 영향을 줄 수 있으므로 현재 운영 코드는 변경하지 않았다.

추가 확인: `update-reservation-full`도 관리자 인증 없이 서비스 역할로 고객 정보와 예약 정보를 변경한다. 배포된 `get-waitlist`는 전화번호만으로 조회할 뿐 아니라 필터 없는 대기 기록 최대 10건의 이름·전화번호·일정 등을 디버그 응답에 포함하도록 작성되어 있다. 입력 전화번호를 로그에 남기는 코드도 있다. `update-waitlist`, `delete-waitlist`는 배포 본문 조회가 실패하여 확인하지 못했다. 엔드포인트 실행 또는 실제 고객 데이터 조회는 하지 않았다.

### 제안 모델과 API 계약 (미구현)

행사 설정은 행사 ID와 승인 상태·시간대·상품 단가·약관 버전, 회차는 행사 ID·시작/식사 종료/정리 종료·운영상 수용 한도를 갖는다. 테이블과 허용 조합 및 회차별 점유는 별도 관리하고, 예약에는 행사·회차·인원·선택 옵션·가격/약관 스냅샷을 기록한다. 예약 상태와 결제 상태, 좌석 점유 및 만료는 별개다. 기존 데이터와의 연결·마이그레이션 방식은 운영 스키마 확인 후 결정하며 현재 마이그레이션 SQL은 없다.

서버 API 제안: 예약 신청은 행사·회차 ID, 인원·페어링 인원, 고객 정보, 약관 버전, 요청별 idempotency key를 수신하고 서버 가격과 좌석 규칙으로 검증한다. 성공은 최소 예약 식별자와 실제 상태를 반환하고, 닫힘·회차 오류·인원 오류·정원 부족·동일 키 다른 요청은 구분 가능한 오류를 반환한다. 조회·취소는 별도 소유 확인을 필요로 하고, 관리자 동작은 별도 인증·인가와 감사 기록을 필요로 한다. 토큰과 고객 정보는 URL·분석 이벤트에 넣지 않는다. 세부 HTTP 스키마는 본인 확인·운영 정책 확정 후 결정한다.

좌석 확인·할당·요청 키 기록은 같은 트랜잭션에서 잠금/제약조건을 사용해야 하며 변경 실패 시 기존 점유를 유지해야 한다. 고객 조회와 관리자 접근을 포함한 모든 직접 호출 경로에도 서버 검증이 필요하다. 단위 테스트만으로 트랜잭션·동시성·RLS 안전성을 증명할 수 없다.

검증 방법: `node --test tests/reservation-policy.test.mjs tests/reservation-request.test.mjs tests/reservation-idempotency.test.mjs tests/reservation-price-snapshot.test.mjs`, `npm run build`, `npx tsc --noEmit`. 고객 신청·조회·취소·관리, 동시성, 마이그레이션, 운영 RLS와 모바일 화면 검증은 미실행이다. 비운영 환경은 별도 Supabase 프로젝트와 가상 데이터로 준비하며 서비스 키를 브라우저에 넣지 않는다. 프로젝트 생성, 환경변수, 정책 적용 절차는 서버 구현과 함께 확정한다.

장애 시에는 신규 접수를 서버에서 닫되 기존 고객 조회·관리 기능을 유지하고, 코드 및 데이터 호환성을 확인한 후 복구한다. 예약 기록을 임의 삭제하지 않는다.

## 권장 구현 순서

1. 운영 데이터 접근 없이 별도 테스트 프로젝트를 준비하고, 읽기 전용으로 운영 스키마와 배포 함수·권한을 대조한다. 접근 권한은 최소화하고 실제 예약 기록을 복제하지 않는다.
2. 행사 식별자와 회차별 날짜·시각·정원, 오픈 상태, 1인 코스·선택 페어링 가격, 예약금 및 조건을 서버 기준으로 모델링한다. 과거 기록의 의미와 조회 호환성을 유지하는 이행·롤백 방안을 먼저 검토한다.
3. 서버에서 행사 상태·한국 시간·입력·가격·정원을 검증하고, 트랜잭션 기반 원자적 재고 확보와 중복 요청 방지를 구현한다. 사용자 입력 가격, 화면 표시 잔여석과 단순 클라이언트 카운트다운은 승인 근거가 아니다.
4. 인증된 관리자만 행사별 조회·수정하도록 권한을 검증한다. 고객 예약 조회는 소유 확인, 최소 정보 반환과 속도 제한을 설계한다. 결제·취소·개인정보 보관/삭제 정책도 검토한다.
5. 기존 폼에서 시각 요소와 입력 컴포넌트만 분리해 행사 페이지의 디자인 토큰을 활용한다. 한국어·영어, 작은 화면, 키보드, 오류·빈 상태를 지원하고 실제 API 호출 없는 미리보기로 우선 확인한다.
6. 서버 계약과 테스트 환경이 준비되면 신규 API를 연결한다. 제출 중 중복 방지, 오류 복구, 접근성, 완료·취소·재조회, 회차 마감과 동시 요청을 검증한다. 기존 경로와 데이터 회귀 테스트를 병행한다.
7. 운영 검토와 명시적 승인 후에만 배포·예약 오픈한다. 운영 DB 마이그레이션은 백업·호환성·롤백·검증 절차와 별도 승인이 필요하다.

## 완료 기준

### 입금 승인과 취소의 로컬 동시성 검증

- 격리된 로컬 PostgreSQL의 가상 데이터로 취소와 관리자 입금 승인 양쪽 순서를 검증했다. 취소가 먼저 확정되면 승인을 거부하고, 승인이 먼저 확정된 뒤 취소되면 입금 확인 기록을 보존한다.
- 권한 없는 승인 거부와 감사 기록 저장 실패 시 승인 롤백도 가상 모형에서 확인했다. 취소는 환불 완료를 의미하지 않는다.
- 관리자 승인 HTTP 처리기에 테스트용 DB 어댑터를 연결해 권한 없는 요청은 저장을 호출하지 않고, 취소된 예약의 승인 요청은 409로 거부하며 기존 감사 기록을 유지하는지 확인했다. 인증과 예약 ID 매핑은 가짜이며 실제 관리자 인증이나 운영 연결 검증이 아니다.
- 로컬 HTTP 응답 유실 테스트는 현재 실행 환경에서 `127.0.0.1` 연결이 `EACCES`로 차단되어 실행하지 못했다. 네트워크 제한이 없는 허용된 환경에서 재실행해야 하며 통과로 간주하지 않는다. 메모리 내 응답 유실·복구 테스트는 별도다.
- 격리 PostgreSQL 실행기에 관리자 취소, 약관 변경, 예약금 변경, 회차·좌석·접수 마감 및 관리자 권한 경합 검사를 포함했다. 2026-11-23 실행 결과 가상 DB 검사 17개가 모두 통과했다. 실제 서버·운영 데이터·실제 인증·환불의 검증은 아니다.
- 가상 메모리 저장소로 신청 접수, 미확정 상태 확인, 관리자 권한·입금 확인 체크, 승인 후 복구와 중복 승인을 연결한 통합 테스트를 추가했다. 실제 은행 입금 확인 및 DB 저장은 수행하지 않는다.
- 비공개 예약 시안의 신청 접수 및 요약 안내에 공통 12시간 입금 기한을 한국어·영어로 표시한다. 실제 입금 계좌·기한 저장·자동 취소와 운영 예약은 연결되지 않았다.
- 행사별 신청·상태 복구·관리자 입금 확인·취소 핸들러를 연결하는 서버 라우터 초안을 추가했다. 접수는 서버 설정이 명시적으로 켜지지 않으면 거부하며 행사 ID를 구분한다. 호스팅·실제 인증·저장소 어댑터·고객 및 관리자 화면 연결은 아직 없어 실제 API가 아니다.
- 같은 출처의 행사 신청·복구 경로로만 요청하는 클라이언트 전송 모듈을 추가했다. 잘못된 행사나 외부 주소는 거부하지만, 이 모듈은 화면·서버에 아직 연결되지 않았으며 GitHub Pages만으로 서버 API가 제공되지는 않는다.
- 이는 테스트용 SQL 모형이며 운영 DB, 실제 계좌 입금 확인, 관리자 화면 및 서버와 연결된 기능의 검증이 아니다. 운영 연결 전 실제 트랜잭션·권한·감사 기록과 환불 절차를 별도로 구현하고 검증해야 한다.

- [ ] 2026 행사의 미확정 값이 고객용 화면에 임의로 표시되지 않는다.
- [ ] 서버에서 닫힌 상태를 강제하고 직접 API 호출도 거부한다.
- [ ] 중복·동시 요청에도 회차 정원을 초과하지 않고 재시도 시 이중 예약이 생기지 않는다.
- [ ] 테스트 환경에서 가격 변조·인가·개인정보 노출·회차 오류·결제/취소와 관리자 권한을 검증한다.
- [ ] 한·영 PC/모바일, 스크린리더·키보드, 기존 예약·관리 경로 및 데이터 호환성을 검증한다.
- [ ] 운영 배포와 예약 오픈은 각각 별도 승인받는다.
